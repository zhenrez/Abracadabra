# SUNNY process lifecycle

The user's current correction requires closing finished workers. Jev receipt47 selected tracked services and owned-tree browser cleanup. `scripts/process-lifecycle.ps1` now records each launched service's PID, creation time, executable path and command digest, including the Python environment launcher and its native child. It serializes startup and shutdown with a workspace-specific mutex. All managed launches use hidden windows.

Use `Start SUNNY.cmd` to start the app and pinned CPU Jev. Repeating it reuses recorded healthy workers. `SUNNY Status.cmd` reports whether tracked identities are still running. `Stop SUNNY.cmd` stops the tracked SUNNY app and tracked CPU/GPU Jev services, waiting for verified workers to exit. It does not terminate processes merely because their name is Node, Python or Command Prompt, and it does not stop unowned plugin connectors or ordinary browser windows.

Service records live under `state/processes/`. Every stop rechecks the current creation time, executable and command digest to reject reused process IDs. Child discovery also binds a fresh identity to its earlier parent, birth, executable and command snapshot and rechecks the parent. Known captured children can be closed after their parent exits. A ready but untracked endpoint is reported as `existing_unmanaged`; startup does not silently adopt it into shutdown ownership. The only legacy migration this turn was the root agent's explicitly authorized CPU launch22996, after its exact command, executable and launch/birth times were compared (difference0.0271011 seconds).

Startup failures clean up the workers started by that attempt. An app-launch failure also closes a Jev worker created by that same transaction, while leaving a reused Jev worker intact. Expected HTTP health remains required before readiness is reported. An unrecognized occupied port refuses a launch.

The occupied-port regression exposed a host limitation: .NET listener enumeration returned zero matches for a TCP listener owned by the very same PowerShell process, while a direct connection succeeded. Evidence is `evidence/lifecycle-listener-enumeration.json`. Receipt51 selected retaining enumeration alone; that output is retained as inadmissible for the no-duplicate acceptance criterion, rather than treated as evidence that the failure passed. A new pool containing two admissible fixes was evaluated through the now-working SuperJev cloud helper. The actual resolved model `jev-1.14.0` selected `tcp_probe_fail_closed` with model mass0.79. The exact request and complete helper result are `evidence/lifecycle-port-admissible-request.json` and `evidence/lifecycle-port-superjev-result.json`. A targeted connection to only the requested loopback port supplements enumeration. A successful connection or inconclusive result refuses launch; only connection refusal permits launch. Its latest run passed12 checks with zero captured owned survivors: real worker/child startup, exact reuse, serialization across two simultaneous Windows PowerShell launches, refusal of unknown occupied ports, startup-failure cleanup, preservation of a same-name control process, date round-trip identity, and both birth-change and stale-snapshot PID-reuse rejection. The stale-snapshot regression failed before the fix; its report remains `evidence/process-lifecycle-before-identity-fix.json`. The insufficient initial probe bound also remains recorded. Current results are `evidence/process-lifecycle-check.json`.

These checks cover the explicit synthetic workers and the current workspace's service controls. They do not prove that arbitrary plugin servers dispose themselves correctly, identify every old process on the computer, or guarantee atomic exclusion against an unrelated application binding a port after the last probe. Source data, global plugin configuration, trained weights and durable user memory were not changed by these lifecycle changes. The final task handoff must independently verify real app/Jev shutdown and any browser or request-worker checks performed by their owners.
